## 成功标准

### 用户成功

**Carlos（买家）— 外国进口商：**
- 开户，法币钱包接入已有合规的或新开户+数字钱包开户
- 无需自行获取美元，即可完成BRL到美元/港币的支付
- Carlos在每个步骤都能看到完整的结算链透明度：
  - Everypay提供当地持牌OTC供应商，这些供应商集成到everypay平台上，OTC根据需要进行BRL的kyt和aml，并最终进行BRL->USDT兑换
  - 存放在Cregis托管中
  - 根据里程碑确认，触发支付审批流（产生文件上传，给人员审批查阅，也能给卖家查看或提交当地otc或监管，证据链）
  - 稳定币支付到收款方的数字货币账户，或自动转成法币后支付给供应商，根据双方约定来执行
  - 如果双方约定法币，通过收款方指定目的地的OTC向供应商交付美元或港币
- 无需暴露加密货币复杂性——仅显示："已付款，供应商已收到。"

**魏（卖家）— 中国大陆出口商（持有香港离岸账户）：**
- 在每个步骤中以完全透明的方式于香港离岸账户收到美元或港币结算：
  - 付款由卖方（最常见）、买方或系统（仅限托管+定时场景）发起
  - 每个付款批次与卖方开具的发票或其它相关约定的文件关联，装箱单也很重要（货物清单，打包的货物清单，卖家直接出的，先考虑文档上传的功能，后期考虑制式化文件）
  - 货币链：本地法币（BRL/ARS）→ 买家所在地OTC → 买家稳定币托管钱包 → 卖家所在地OTC → 卖家法币账户（主流）；本地法币（BRL/ARS）→ 买家所在地OTC → 买家稳定币托管钱包 → 买家稳定币账户 (订单流程 以支付方为主的流程；进出口互动系统包括：2 关务（可能包含合同），物流（可能包含合同）和财务（独立系统），先实现形式上提供证据，解决快速支付和借助稳定币跨国支付即可，不用强制支付流程；实质上审查是后续实现)
  - 托管质押可选（EXACT/OVER/UNDER）（未来考虑，先考虑直接付款）
  - 按协议类型管理汇率风险
  - 里程碑确认释放（已发货、海关清关）
  - 美元或港币转入香港离岸银行账户（mvp借助类似U卡，来实现usdt->法币兑换？用于演示。内部讨论）
- 根据保护措施为每笔结算生成风险评分
- 如货物未在约定时间内收到，可启动争议机制
- 下载完整证据包用于监管合规

**双方：**
- 整个结算链全程可见实时结算状态
- 服务两类买家群体：非正式贸易商（速度优先）和结构化进口商（合规优先）

### 商业成功

- 结算完成率 >99%的已发起结算达到SETTLED状态
- 每笔结算的证据包完整率达100%
- MVP启动标准：10笔端到端结算成功且用户反馈积极
- 结算速度目标：稳定币环节T+0完成（整链时间待定）

### 技术成功

- Cregis托管仅在物流合作方核实里程碑确认后释放USDT
- Everypay HK将USDT转换为美元或港币，并附完整时间戳审计跟踪转入魏的香港离岸账户
- 证据包具有时间戳、防篡改特性，监管机构可随时调取
- 100%监管合规：香港牌照+香港离岸账户合规

### 合规（核心/不可协商）

- 每笔结算必须生成完整的时间戳证据包，作为交易活动的审计和监控凭证
- 100%遵守香港牌照要求
- 物流合作方提供的里程碑数据必须具有防篡改性和时间戳

## 产品范围

### MVP — 最小可行产品

- **核心市场**：巴西BRL和阿根廷ARS走廊（双走廊MVP）
- **结算类型**：基于里程碑的延期结算（定金 → 已发货 → 海关清关 → 尾款）
- **结算流程**：
  1. 结算由卖方（最常见）、买方或系统（仅限托管+定时场景）发起
  2. 每个批次与卖方开具的发票关联
  3. 买方将本地法币（BRL/ARS）转入Everypay收款账户
  4. Everypay在内部将本地货币转换为USDT
  5. USDT存放在Cregis托管中（如已启用）
  6. 物流合作方提供里程碑数据——已发货、海关清关
  7. Cregis在里程碑确认后释放USDT至Everypay HK
  8. Everypay HK将USDT转换为美元或港币
  9. 美元或港币转入魏的香港离岸银行账户
  10. 魏收到完整证据包（按批次）
- **3货币链**：本地法币（BRL/ARS）→ USDT稳定币 → 美元或港币
- **汇率锁定**：完整实现——PRELOCK（发票时约定汇率并锁定）和INTIME（付款时汇率）两种方式均可用
- **托管协商**：完整的双边协商流程——双方均可提议超额托管押金、协商条款并批准
- **托管金额类型**：EXACT、OVER、UNDER及缺口处理
- **买家群体**：非正式贸易商和结构化进口商
- **平台**：仅基于Web的UI（MVP无移动应用）
- **物流集成**：仅内部集成（MVP无物流合作方外部API）
- **启动标准**：最少10笔结算成功且用户反馈积极

### MVP范围外

- 额外走廊（哥伦比亚COP、秘鲁PEN）—— 第二阶段
- 移动应用
- 汇率锁定以外的FX对冲工具（远期合约、期权）
- 补贴文档准备服务（提供证据包；申请由魏负责）
- 合作伙伴/渠道推荐计划
- 第三方集成API
- 大型机构买家（政府采购、国有企业）

### 增长功能（MVP后）

- 俄罗斯，额外拉美走廊：哥伦比亚COP、秘鲁PEN
- 移动应用
- FX对冲工具：大型用户的远期合约、期权
- 物流合作方webhook集成API
- 补贴文档准备自动化
- 额外市场扩张（东南亚）

## 结算配置模型

Everypay支持多维结算配置以适应不同的贸易场景。

### 配置维度

| 维度 | 选项 | 描述 |
|-----------|---------|-------------|
| **托管** | 必需/非必需 | USDT存放在Cregis托管中；保护买方或直接结算 |
| **汇率方法** | PRELOCK / INTIME | 初始化时锁定汇率或付款时协商汇率 |
| **托管金额** | EXACT / OVER / UNDER | USDT金额相对于付款义务 |
| **托管结构** | 一次性/分阶段 | 单次托管或基于里程碑的分批托管 |
| **发起方** | 卖方/买方/系统 | 大多数结算由卖方发起；系统仅在托管+定时场景下发起 |

### 汇率风险管理

| 场景 | 汇率保护 | 机制 |
|----------|----------------|-----------|
| 托管 + PRELOCK | 初始化时汇率锁定 | 买方受保护；卖方承担释放前的风险 |
| 托管 + INTIME | 善意协商 | 48小时SLA；延迟汇率惩罚；协商失败自动升级至中立第三方 |
| 无托管 | 双边协议 | 无自动保护；双方直接协商 |

### 托管金额类型

| 类型 | 描述 | 缺口处理 |
|------|-------------|-------------------|
| **EXACT** | USDT = 约定汇率下的精确付款义务 | 不适用 |
| **OVER** | 高于精确值的缓冲（卖方保护） | 卖方受到汇率不利波动的保护 |
| **UNDER** | USDT < 付款义务 | 买方：(1) 直接支付缺口，或 (2) 请求卖方补充托管 |

### 争议机制

- **触发条件**：买方未在约定时间内收到货物
- **买方行动**：请求部分或全额托管退回
- **惩罚托管**：双方均可追加托管作为惩罚保证金
- **升级路径**：直接协商 → 48小时SLA → 自动升级至中立第三方
- **第三方裁决**：审核证据；决定部分/全额释放或惩罚执行

### 风险评分评估

平台根据保护措施为每笔结算计算**风险评分（0-100）**：

| 风险因素 | 影响 | 评估 |
|-------------|--------|------------|
| 已启用托管 | 高 | 已启用 = 较低风险 |
| 汇率方法 | 中 | PRELOCK < INTIME < 无托管 |
| 托管金额类型 | 高 | EXACT < OVER < UNDER |
| 托管结构 | 中 | 分阶段 < 一次性 |
| 争议历史 | 高 | 既往争议增加风险 |
| 付款规模 | 中 | 越大风险越高 |
| 走廊波动性 | 中 | FX波动性越高风险越高 |

**风险报告包括：**
- 总体风险评分及等级（A/B/C/D）
- 各风险因素明细
- 建议保护措施
- 升级风险标记
- 承诺前买卖双方均可查看

## 用户旅程

### 旅程1：Carlos Mendez — 买家（成功路径）

**开场场景：** Carlos欠中国供应商相当于50,000美元的货款。他的客户以BRL付款，但他无法获得美元来支付供应商——这是货币获取缺口，而非偏好。他担心BRL每小时都在贬值。

**上升行动：** Carlos登录Everypay，输入50,000美元等值的BRL。Everypay预先显示汇率和费用。Carlos确认。他将BRL转入Everypay的巴西收款账户。完成转账的那一刻，Everypay显示："您已为供应商锁定了X美元。您的BRL已受到市场波动保护。"——Carlos感到**释然**，而非仅仅是"交易完成"。

**高潮：** Carlos实时追踪付款：BRL收到 → USDT购买 → Cregis托管 → 货物已发货 → 海关清关 → 美元或港币交付给供应商。他看到"付款完成——供应商已收到美元/港币。"

**结局：** Carlos的供应商无需Carlos获取美元就收到了美元/港币。Carlos进行下一次付款。情感回报是**焦虑 → 释然**。

### 旅程2：魏 — 出口商（成功路径）

**先决条件（必须首先完成）：**

1. **KYB验证**：魏（卖方）和巴西买方都必须：
   - 完成商业注册验证
   - 提交实益所有权声明（>10%股东）
   - 提供授权签字人名单
   - 通过AML/CTF风险分类
   - 在交易前获得平台批准

2. **建立贸易关系**：在任何付款之前：
   - 魏和巴西买方在Everypay上建立交易对手关系
   - 双方同意平台条款和条件
   - 贸易历史开始（首笔结算建立信任评分）

3. **付款协议**：每笔结算需要：
   - 定义条款（托管、汇率方法、金额类型）的贸易付款协议
   - 双方合同的引用
   - 每个批次的卖方发票引用

**旅程从此开始：**

**开场场景：** 魏的公司向巴西买方销售货物。已在Everypay上建立贸易关系。魏为每个付款批次开具发票。他需要在其香港离岸账户获得可靠的美元或港币结算，并必须生成用于监管合规的审计就绪文档。

**上升行动：** 
- 魏在Everypay上创建具有约定条款（托管、汇率方法、金额类型）的发票
- 创建引用发票的付款协议
- 买方接受条款并发起付款
- 魏实时监控结算
- 结算路径取决于配置：
  - 有托管：魏追踪里程碑确认（已发货、海关）
  - 无托管：付款确认后直接结算
- 汇率风险取决于汇率方法：
  - PRELOCK：汇率锁定后魏受到保护
  - INTIME：双方协商；魏监控汇率协议
- 如发生争议（未收到货物）：魏可回应托管退回请求或升级

**关键决策点：**
1. **托管配置**：魏为每位买方设置托管必需/可选
2. **汇率方法选择**：根据风险偏好选择PRELOCK或INTIME
3. **托管金额**：根据信任级别选择EXACT/OVER/UNDER
4. **里程碑确认**：魏在释放托管前验证已发货/海关
5. **争议回应**：魏可追加惩罚托管或升级至第三方

**高潮：** 魏下载每个批次的完整证据包：发票、合同、物流里程碑（已发货、海关清关）、结算收据——均为时间戳、防篡改、格式化的监管提交文档。魏在承诺前审核风险评分报告。

**结局：** 魏的付款以美元或港币结算至其香港离岸账户。证据包完整。信任已为未来交易建立。

### 旅程3：魏的CFO — 财务和风险审批人（高价值结算）

**开场场景：** 魏提交了一笔250,000美元的结算。Everypay策略标记："高价值——需要财务审查。"

**上升行动：** CFO打开Everypay的审批队列，看到：
- 交易对手详情：Carlos的公司、巴西注册信息、交易历史
- 结算摘要：250,000美元，BRL → 美元/港币走廊，初始化时的汇率
- FX敞口：当前USDT/美元或USDT/港币汇率及交付时的预计金额
- 托管金额审核中
- 风险评分及明细
- 策略检查：单笔交易限额内 ✓

**关键决策点（财务风险管理）：**

1. **汇率风险检查** — CFO评估："以当前USDT/美元或USDT/港币汇率，Everypay HK能否接受此付款而不产生不可接受的FX敞口？"
2. **流动性时机** — CFO决定："现在从托管释放USDT至香港，还是等待资金池达到门槛以提高转换效率？"
3. **托管金额审核** — 如已协商超额托管：CFO审核并批准缓冲金额
4. **风险报告审核** — CFO评估总体风险评分并标记

**升级策略（可按账户配置）：**
- CFO → 财务主管 → 风险经理（客户定义的链条）
- 以下情况自动升级：自初始化以来汇率变动>X%、付款>金额门槛、走廊波动触发器、风险评分超过门槛
- 时间限制：48小时；如无响应：升级至下一审批人

**结局：** CFO批准。Cregis释放 → Everypay HK → 美元/港币 → 魏。完整审计跟踪：批准人、批准时间、评论、批准时汇率。

### 旅程4：魏的运营团队 — 结算监控（内部）

**开场场景：** Everypay的运营团队监控结算管道中的问题。

**上升行动：** 仪表板显示所有活跃结算：阶段、任何卡住的付款、FX汇率、托管状态、风险评分。一个警报触发——来自物流合作方的里程碑确认未能到达。

**高潮：** 运营调查：物流合作方系统宕机？数据不匹配？联系物流合作方并解决问题。如需手动干预：运营可在授权下触发里程碑确认。

**结局：** 结算完成。事件记录用于审计。如适用，SLA违规被标记。

### 旅程5：Carlos — 汇率锁定场景

**开场场景：** Carlos发起一笔大额付款。BRL波动剧烈——他需要FX保护。

**上升行动：** Carlos在确认前看到汇率锁定选项。他锁定汇率（PRELOCK）。BRL后来大幅贬值。Carlos以锁定汇率付款——他的供应商收到约定的美元等值金额。

**结局：** Carlos免受BRL贬值影响。供应商收到了发票时约定的美元金额。Carlos此后所有大额付款都使用汇率锁定。

### 旅程6：魏 — 可选托管（可信合作伙伴）

**开场场景：** 魏和Carlos已完成20笔成功结算。魏信任Carlos的业务。

**上升行动：** 魏创建新发票并为此货件选择"无托管"。Carlos收到发票，接受无托管条款。魏批准。

**流程：** Carlos支付BRL → Everypay转换 → 美元/港币 → 直接给魏。无里程碑持有。无Cregis托管。

**结局：** 结算更快。费用更低。双方都从已建立的信任中受益。

### 旅程7：魏 — 超额托管协商

**开场场景：** USDT/美元或USDT/港币汇率波动剧烈。魏希望防止进一步波动。

**上升行动：** 魏要求高于精确美元义务5%的超额托管缓冲。Carlos收到请求。Carlos提议3%。魏接受。

**流程：** Carlos追加3%的托管。里程碑确认。魏接受。结算进行。

**结局：** 双方协商达成一致。超额托管是一种透明的协商机制——而非惩罚。

### 旅程8：Carlos — INTIME汇率协商

**上升行动：**

- Carlos提议一个汇率，魏还价
- 协商开始，48小时SLA
- 如Carlos恶意拖延：适用汇率惩罚，SLA违约后自动升级至第三方

**结局：** 双方在SLA内达成汇率协议，或第三方公正裁决。结算进行。

**开场场景：** 物流合作方确认"已发货"，但魏声称货物在运输中损坏。

**上升行动：** 魏对里程碑提出争议。结算在Cregis托管中暂停。Carlos和魏协商。物流合作方提供额外文档。

**结局：** 双方达成协议。资金按新条款释放。完整争议记录用于审计。任何一方均可追加惩罚托管。

## 贸易付款协议框架

**核心概念：**
Everypay促进买卖双方之间的**贸易付款协议**。协议是核心产品对象——不仅仅是付款，而是规范结算方式的结构化、可执行合同。

### 协议 ↔ 贸易文档关系

```
贸易包（完整记录）
├── 合同（买卖双方之间的合法贸易协议——外部）
├── 发票（卖方创建，引用合同）
├── 海关文档（运输、清关——外部）
├── 贸易付款协议（Everypay——新增）
│   ├── 汇率方法：PRELOCK | INTIME
│   ├── 托管条款：必需 | 可选
│   ├── 托管金额：EXACT | OVER | UNDER
│   ├── 托管结构：一次性 | 分阶段
│   ├── 里程碑批次
│   ├── 审批链
│   ├── 合同+发票引用
│   └── blockchain_ref（预留用于未来链上演绎）
└── 修正案（带版本，双方签署）
```

### 协议格式

- **结构化数据协议**——机器可读、可审计、带时间戳
- 旨在作为**正式法律文档**长期服务
- **链下协议**，预留`blockchain_ref`字段用于未来链上智能合约映射
- 双方数字签名提供法律效力

### 汇率确定 — 两种方法

| 方法 | 描述 |
|--------|-------------|
| **预先锁定** | 发票时约定汇率，无论市场波动与否。如果BRL贬值，Carlos受到保护。如果USDT/美元或USDT/港币走势不利，魏承担风险。 |
| **即时** | 付款/批次时设定汇率。双方均可见当前市场汇率。48小时SLA协商；失败时自动升级至第三方。 |

### 托管 — 三种金额类型 + 结构

| 金额类型 | 描述 |
|-------------|-------------|
| **无托管** | 高信任关系。Carlos支付BRL → Everypay转换 → 美元/港币 → 直接给魏。 |
| **精确托管** | USDT金额 = 约定汇率下的精确美元义务。存放在Cregis直到里程碑确认。 |
| **超额托管** | 魏要求高于精确值的缓冲（用于FX风险）。双方协商并批准超额金额。 |
| **不足托管** | USDT < 付款义务。买方：(1) 直接支付缺口，或 (2) 请求卖方补充托管。 |

| 结构 | 描述 |
|-----------|-------------|
| **一次性** | 整个结算的单次托管 |
| **分阶段** | 基于里程碑的分批（定金 → 已发货 → 海关清关 → 尾款） |

### 协议创建流程

```
魏创建发票
  → 附加贸易付款协议作为独立文件
  或
  → 在发票内嵌入付款批次条款

协议引用：
  → 合同 #CTR-XXX
  → 物流里程碑（来自物流合作方oracle）
  → 海关引用

协议状态：DRAFT → PROPOSED → NEGOTIATED → SIGNED → ACTIVE → FULFILLED / DISPUTED / CANCELLED
```

### 模板库

Everypay提供**平台级协议模板**（非卖方创建）：
- 按走廊的模板（巴西BRL默认模板）
- 按交易规模层的模板
- 按关系信任级别的模板

魏将完成的协议保存为与同一买方重复交易的**可重用模板**（例如"魏↔Carlos标准条款"）。未来发票从保存的协议模板自动填充。

### 审批链（可按卖方账户配置）

```
策略配置（按账户）：
  ├── 自动接受门槛：汇率变动 < X%
  ├── 托管必需：始终 | 从不 | 基于门槛
  ├── 审核链：CFO → 财务主管 → 风险经理
  ├── 风险评分门槛：> X时自动升级
  └── 时间限制：默认48小时

结算触发审核的情况：
  ├── 付款 > 金额门槛
  ├── 汇率自初始化以来变动 > X%
  ├── 走廊波动触发器
  ├── 超额托管金额超过Y%
  └── 风险评分超过门槛
```

### USDT余额状态

| 状态 | 描述 | Carlos能提取吗？ |
|-------|-------------|---------------------|
| 可用余额 | USDT存放在平台上，未承诺 | 可以，随时 |
| 已锁定用于结算 | 已承诺待处理结算 | 不可以 |
| 托管中（Cregis） | 存放在Cregis托管中，等待里程碑 | 不可以 |
| 已释放至香港 | USDT已释放至Everypay HK用于转换 | 不可以 |
| 批次已完成 | 美元或港币已交付给魏，结算完成 | 不适用 |

### 争议解决

- **触发条件**：买方未在约定时间内收到货物
- **买方行动**：请求部分或全额托管退回
- **惩罚托管**：双方均可追加托管作为惩罚保证金
- **升级**：直接协商 → 48小时SLA → 自动升级至中立第三方
- **第三方**：审核证据，决定部分/全额释放或惩罚执行

### 平台许可（可执行性）

Everypay必须获得**许可**才能作为可执行的贸易付款平台运营：
- 香港支付服务提供商牌照
- 迪拜托管牌照（Cregis）
- 买卖方司法管辖区要求的其他牌照

通过Everypay的许可框架、数字签名和不可变审计日志，协议在买卖双方之间具有**法律约束力**。

## 创新与新模式

### 发现的创新领域

**1. 贸易到付款证据链**
证据包是核心产品交付物——而非合规复选框。每笔结算都生成完整的时间戳、防篡改证据包（发票、合同、物流里程碑、结算收据），魏将其用于监管合规。这是第一个监管合规*为用户创造价值*而非仅仅保护平台的平台。在拉美-中国走廊中没有直接同类产品。

**2. 带物流Oracle的稳定币托管**
Cregis持有USDT针对可验证的外部条件——物流里程碑确认（已发货、海关清关）。任何一方都无法单方面操纵。这是一个无需信任的条件释放机制，而非简单托管。在发展中市场-中国贸易走廊中为Everypay独有。

**3. 多维结算配置**
平台内部完整的贸易关系管理：汇率方法（预先锁定与即时）、托管模型（无/精确/超额/不足）、托管结构（一次性与分阶段）、里程碑批次、审批链和可配置升级策略。贸易付款协议是结构化数据合同——不仅仅是支付通道，而是具有完整审计历史的协商性、版本化贸易关系。

**4. 风险评分评估系统**
平台根据已采取的保护措施为每笔结算计算风险评分（0-100）。风险报告在承诺前为双方提供透明度，实现知情决策。

**5. 按走廊合规架构**
合规逻辑从第一天起就按走廊设计。随着阿根廷ARS与巴西BRL并列MVP，Everypay从一开始即实施双走廊合规——BCRA（阿根廷）和BCB（巴西）框架并行运行。

### 验证方法

- MVP验证10笔成功的BRL→美元/港币结算且用户反馈积极
- 每笔结算的证据包完整率达100%
- 结算完成率 >99%
- 成功引入非正式贸易商和结构化进口商

### 风险缓解

- **走廊扩张风险：** 按走廊合规架构允许按市场逐步验证
- **监管风险：** 香港/迪拜许可提供既定监管地位；巴西合作方有BCB授权
- **FX风险：** 汇率锁定机制在BRL波动期间保护Carlos；超额托管为魏提供缓冲
- **技术风险：** Cregis提供机构级托管基础设施；具有政策强制签名的成熟稳定币保险库

## 非功能需求

### 性能

- **结算处理：** 稳定币环节（USDT转换）T+0完成；美元/港币跨境转账T+1完成
- **实时状态：** 状态变更后30秒内买卖双方可见结算状态更新
- **证据包调取：** 监管机构请求后48小时内可调取完整证据包
- **系统响应：** UI操作（发票创建、付款发起、状态查询）在3秒内完成
- **并发用户：** 系统支持每走廊100个并发活跃结算且无性能下降

### 安全性

- **数据加密：** 所有KYC/KYB文档静态加密（AES-256）；传输中所有数据加密（TLS 1.3）
- **访问控制：** RBAC在API层面强制执行；不可能发生跨租户数据访问
- **制裁筛查：** 所有用户实时接受OFAC、联合国、欧盟和当地制裁名单筛查
- **审计日志：** 所有结算事件记录时间戳、参与者、行动和哈希引用；不可变
- **冻结令执行：** Cregis在收到后15分钟内强制执行冻结令作为硬性阻止
- **渗透测试：** 需要年度第三方渗透测试
- **KYC数据保留：** KYC文档最少保留7年；仅合规角色可访问

### 可扩展性

- **走廊扩展：** 平台架构支持新增走廊而无需修改核心平台
- **用户增长：** 系统从MVP（10笔结算）扩展到1000+笔结算/月，性能下降<20%
- **地理分布：** 无需基础设施修改即可支持50+国家用户
- **成交量峰值：** 在市场波动期（BRL/ARS FX事件）处理正常成交量3倍

### 可靠性

- **结算完成率：** >99%的已发起结算达到SETTLED状态
- **证据包完整率：** 100%的结算产生完整证据包
- **系统正常运行时间：** 99.5%正常运行时间（计划维护除外）
- **灾难恢复：** 恢复点目标（RPO）= 0；恢复时间目标（RTO）< 4小时

- **数据驻留：** KYC/KYB文档按当地法规存储在适当的司法管辖区数据中心
- **AML合规：** FATF一致的AML/CTF计划；在监管时限内报告可疑活动
